# Life Pilot First Test Project Plan

Status: PROPOSED PLAN FOR REVIEW. Version 0.1. Prepared 9 November 2026.
Owner: Gary McCourt. Coordination: Folio.
This plan follows documentation approval and does not authorise construction.

## Outcome

Deliver a bounded, explainable Life Pilot demonstration, test it against recorded expectations and produce an evidence-backed investor pack. Preserve the approved commercial MVP direction without pretending this first test completes the wider product.

## Delivery sequence and dependencies

P1 Documentation: review the foundation, first-test scope, governance, website brief and demo instructions. Correct historical terminology in derivative records. Output: G1 decision with exact document versions. Owner: coordinator prepares; Gary decides.

P1A Approved source promotion: for each approved change affecting a controlled baseline, perform only the authorised source update and verify its exact revision and readback under G1A. If a merge or canonical-location decision is required, return to Gary. Output: verified approved source index or a reasoned not-applicable disposition. Dependent implementation cannot start while this step is pending.

P2 Project plan: confirm implementation owner, environment, repository baseline, available budget, estimated effort, scenario rules and test matrix. Output: G2 bounded build packet. This phase cannot close before G1.

P3 Build: implement only the approved slice and website scope. Prefer existing compatible components and preserve private MYOH structures. Output: candidate revision, implementation notes and maker tests. Starts only after G2.

P4 Test: independently execute functional, calculation, repeatability, error, privacy, accessibility and regression checks on the candidate. Output: test report and defect disposition. Changed code invalidates affected test evidence until rerun.

P5 Demo readiness: verify reset, script, dataset and private demonstration environment. Output: G4 decision. No live release is included.

P6 Investor pack: revise the existing investor working document with verified screenshots, test findings, limitations, commercial hypotheses, funding-use logic and founder details. Output: G5 reviewed pack. Do not call an untested demo validated or replace missing traction with forecasts.

P7 External activity: website publication, partner outreach and participant testing are separate approvals. Prepare decisions only when prerequisite evidence exists.

## Work packages and acceptance

WP01 Source reconciliation. Deliver a source index and drift log. Accept when every product term and active/parked reference is consistent with the locked source; version anomalies are visible.

WP02 Foundation and scope. Deliver mission/vision proposals, first-test journeys, exclusions and acceptance criteria. Accept when Gary has a clear approve/revise decision without implied code authority.

WP03 Governance. Deliver operating procedure, skills/capability inventory, gate matrix, decision/action records and exception process. Accept when each decision identifies authority and resulting action.

WP04 Demo support and website specification. Deliver facilitator script, reset checklist, copy, page structure and publication checklist. Accept when copy makes no unverified claims and the website does not collect personal data by default.

WP05 Implementation readiness. Deliver exact baseline, affected files/components, proposed rules, dependencies, test fixtures and rollback. Accept only after repository and runtime inspection. No stack, hosting or migration is assumed.

WP06 Build and assurance. Deliver candidate plus independent evidence for FT01–FT08. Accept when required results pass and defects have explicit disposition.

WP07 Investor production. Deliver final narrative/deck, one-page summary, evidence appendix, risks, GTM hypotheses and use-of-funds assumptions. Accept when figures and claims have sources and Gary approves recipient-facing material.

## Scheduling

No fixed delivery date is promised before implementation discovery. The current approved commercial MVP target is January–March 2027. Delivery feasibility remains unvalidated; the target is retained and is not silently superseded by this first-test plan.

Planning assumption for one bounded synthetic demo: documentation review 1–2 working sessions; implementation readiness 1 session; build 3–8 focused working days; independent testing and correction 2–5 days; final investor production 1–3 days. These are estimates, not commitments, and exclude participant recruitment, procurement, legal review and production release. Validate after G1/G2. Human review availability and technical gaps may dominate elapsed time.

No external spend is authorised. Any paid service, subscription, domain, hosting, design work or legal engagement requires an identified need, cost and approval.

## Critical path

Approved scope → approved-source promotion and verification where applicable → confirmed baseline and rules → build approval → candidate → independent tests → corrections and retest → demonstration acceptance → final investor evidence.

Website copy can progress during documentation; website code cannot bypass G2. Commercial research and GTM planning may progress without outreach. Parked products are not parallel work packages.

## Risks and responses

R01 Stale sources: locked terminology check and explicit supersession references.
R02 Real data contamination: fictional datasets, pre-commit review and screenshot inspection.
R03 Opaque signals: trace rule/input/output and reject unsupported certainty.
R04 Scope expansion: requirement-to-change mapping and Gary change gate.
R05 Test evidence drift: record exact revision and rerun affected cases after changes.
R06 Overstated market demand: separate hypothesis, interview evidence, pilot evidence and paying customer.
R07 Unavailable specialist capability: log gap; block dependent high-risk work only.
R08 Existing architecture cannot support slice safely: return an options assessment, not an unapproved migration.
R09 Commercial target pressure: reduce the test slice through approval rather than bypassing controls.

## Reporting

At each material milestone report completed artifacts, exact revision, evidence, unresolved blockers and one next decision. Do not report planned tests as passed or a proposed gate as approved. Keep every idea in the decision/backlog record rather than silently adding it to the build.

## Completion definition

This programme is complete when agreed documents and plan are approved, the bounded demo has independent test evidence and Gary's acceptance, the investor pack is finalised against that evidence, and every remaining release or pilot action has an explicit status. Public release and investment success are not completion claims.
